# partest-load

Нагрузочный харнесс семейства **partest**: профили нагрузки по времени, метрики насыщения и
деградации, HTML-дашборд.

**PyPI:** [`partest-load`](https://pypi.org/project/partest-load/), версия — см.
`docs/wiki/status.md` · **Лицензия:** MIT (`LICENSE`) · **Страница пакета:** `docs/PYPI.md`,
а не этот файл · **Версии:** semver, политика — в начале `CHANGELOG.md`

```bash
pip install 'partest-load[report]'   # с PyPI, вместе с дашбордом
pip install -e ".[dev]"              # из рабочей копии плюс всё, что нужно прогону тестов
```

Python 3.10–3.14.

## Что делает

Нагрузка задаётся **временем, а не количеством запросов** — это принципиально: интересует
не «сколько мы отправили», а «где система перестала держать».

| Профиль | Что делает | Что показывает |
|---|---|---|
| `linear` | постоянная нагрузка | держит ли систему на заданном уровне |
| `ramp` | плавный рост до плато и спад | где начинается деградация |
| `stress` | ступенчатый рост темпа и одновременности до отказа | точка насыщения и наклон деградации |
| `batch` | конечный список (варианты × `repeat_count`) на одном уровне | успевает ли система пройти список |

Метрики: RPS, перцентили задержки (ближайший ранг — одно определение на семейство), средняя
и максимальная задержка, доля успехов и ошибок, размеры ответов. Запросы, не вернувшиеся к
концу фазы и выдержки, — неуспешные замеры `cancelled` с длительностью до отмены (нижняя
оценка); они входят и в долю ошибок, и в задержки; для `stress` — точка
насыщения и наклон деградации. Выводы (насыщение, деградация) строятся на перцентилях, а не
на средней.

Ключи профилей и описаний эндпоинтов, что каждый из них делает и чего не делает —
`docs/wiki/components/configuration.md`.

## Отношение к partest

Пакет **не изобретает то, что уже есть в семействе**. Это граница, а не текущее состояние:
перечисленное ниже ещё не подключено — см. «Статус».

| Задача | Откуда берётся |
|---|---|
| Авторизация, мульти-ролевые токены | `partest.TokenManager` |
| Заголовки, параметры, привязка токена | `partest.http.Config`, `HeadersBind` |
| Список эндпоинтов и шаблоны путей | `partest.openapi`, `partest.path_match` |
| Редактирование секретов в отчёте | `partest.redact` |

Отсюда следствие: профиль пишется **на контракт**, а не на руками перечисленные URL. Список
эндпоинтов берётся из спецификации, и при её изменении профиль не разъезжается молча.

## Прогон опознаётся операцией

Личность прогона — **операция**, записанная в форме `МЕТОД /путь`, например
`GET /v1/items/{id}`. Операция выводится из описания эндпоинта (метод и путь там уже есть),
отдельно её указывать не нужно, и разойтись с тем, что нагружали, она не может.

Ключ `--endpoint` остаётся **подписью**: имя, которым вы назвали эндпоинт у себя. Оно пишется
в прогон и показывается в отчёте, но ничего не опознаёт — переименуете, и история прогонов
останется на месте.

Это различие видно в раскладке результатов:

```text
<корень>/<ключ операции>/<профиль>/<время>__<ключ операции>__<профиль>__<hex>.json
<корень>/_latest/<ключ операции>__<профиль>.json        указатель на последний прогон
```

Ключ операции — безопасное имя файла: читаемый остаток плюс восемь знаков хеша
(`get-v1-items-id-3f2a1b0c`). Преобразование необратимо, поэтому сама операция лежит **внутри
файла прогона** в исходном виде, вместе с `{placeholders}` пути: по ней замер сводится с
внешними данными о том же эндпоинте, и расшифровывать имя каталога не нужно.

Операция проверяется до нагрузки, вместе с остальными именами: отказ записи после двадцати
минут прогона — не то, что должно обнаруживаться в конце.

Поле названо `operation`, а не `scope`, намеренно: слово `scope` занято контрактом
артефактов, владелец которого — другой пакет семейства, и значит там оно другое. Одно слово
на два понятия разошлось бы уже после первой выгрузки, когда раскладка каталогов станет
наблюдаемым интерфейсом.

## Устройство

```text
partest_load/
  cli.py       точка входа: все пути приходят аргументами
  operation.py операция прогона: «МЕТОД /путь» и её ключ в имени файла
  configs/     описания эндпоинтов и профилей (в пакете — только схемы, не значения)
  core/        клиент, метрики, пейсинг, воркер, раннер
  engines/     реализации профилей: linear, ramp, stress, batch
  storage/     сохранение результатов и схемы данных
  reporting/   HTML-дашборд (Jinja2 + Plotly), шаблоны в reporting/templates/
  artifacts.py выгрузка `load.profile` — ПЛАНИРУЕТСЯ, модуля пока нет
```

## Быстрый старт

Описания эндпоинтов и профиль — ваши файлы: пакет знает формат, значения остаются у вас.
Пути всегда указываются явно, ничего не ищется относительно текущего каталога.

```bash
pip install 'partest-load[report]'

partest-load \
  --endpoints my/endpoints.yaml --endpoint orders_create \
  --profile my/profiles/ramp.yaml \
  --results-root out/load --save-raw \
  --report out/load/dashboard.html
```

`--dry-run` разбирает и показывает конфигурацию и план (фазы, потолок, темп), не отправляя
ни одного запроса.
`--report-only` пересобирает дашборд по уже сохранённым прогонам.

**`--save-raw` пишет в файл прогона тела запросов целиком, до 500 символов тела ответа на
каждую ошибку и адрес каждого запроса с подставленными `path_params`, без маскировки.** Там бывают учётные и персональные данные; команда
предупреждает об этом при включении. Файл прогона с сырыми результатами и дашборд по нему не
публикуют и не передают как есть.

Дашборд открывается в закрытом контуре: plotly.js вшивается в файл, ни одной ссылки наружу
в нём нет. Без extra `report` прогон работает и результат сохраняется — не будет только
HTML-отчёта.

## Статус

Линия `0.x`, выпуски на PyPI; текущая версия и что дальше — `docs/wiki/status.md`. Код
перенесён из прототипа `github.com/Dec01/load` со снятием проектного домена: конкретные
эндпоинты, адреса стендов и учётные данные остаются в конфигурации потребителя, в пакете —
схемы и движки.

Ещё **не** сделано, и полагаться на это нельзя: выгрузка артефакта `load.profile`
(`artifacts.py`), переиспользование `partest` из таблицы выше (`TokenManager`, `http.Config`,
`openapi`, `redact`), маскировка сырых результатов (`--save-raw`), раскрытие переменных
окружения в YAML и выключение проверки TLS.
