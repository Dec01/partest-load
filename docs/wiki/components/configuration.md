# Конфигурация и командная строка

Два файла потребителя — описания эндпоинтов и профиль — и флаги `partest-load`. Здесь —
что каждый ключ **делает**, а не только как называется. Значения в пакет не попадают, см.
[[components/overview]].

## Описание эндпоинта

YAML-отображение «ключ → описание»; ключ — то, что передают в `--endpoint`, и подпись
прогона. Неизвестный ключ — ошибка разбора.

| Ключ | Что делает |
|---|---|
| `name`, `method`, `headers`, `query_params`, `timeout` | как называются |
| `base_url` | база без `?query` и `#fragment`, в том числе пустых (ошибка разбора). `user:password@` уходит только Basic-авторизацией на каждый запрос (`EndpointConfig.basic_auth()`; пустые логин и пароль — без авторизации, явный `Authorization` не перекрывается). Наружу адрес выходит без него и без `?query`/`#fragment` — `url()`, журнал, вывод, файл прогона, `repr`, — как бы описание ни получило адрес (разбор, присваивание, `model_copy`, `model_construct`); `model_dump()` отдаёт поле как задано |
| `path` | путь; может содержать `{placeholders}`. Операция прогона — `МЕТОД` и этот путь **шаблоном** |
| `path_params` | значения `{placeholders}`, общие для всех вариантов |
| `payloads` | варианты запроса, ротируются по кругу поровну: `body` (для POST/PUT/PATCH) и `path_params` варианта — перекрывают общие |
| `batch_mode`, `repeat_count` | **ничего**; принимаются ради старых файлов и предупреждают `ConfigKeyWarning`. Batch задаётся профилем |

**Адрес запроса собирается только из `base_url`, `path` и `path_params`.** Тело на адрес не
влияет ни одним своим ключом; `full_url` в теле — обычное поле тела, и разбор об этом
предупреждает (имя похоже на адрес). Конечный список ресурсов задаётся вариантами с
`path_params`.

**Подстановка.** Значение кодируется целиком, вместе с косой чертой, а значение из одних
точек (`.`, `..`) — как `%2E`: подставленный идентификатор не меняет путь и не уводит
нагрузку выше шаблона. Правила те же, что у `partest.tracking._id_segment`. Пустое значение
и имя в `path_params`, которого нет в пути, — ошибки разбора; пустой плейсхолдер `{}` и
непарная скобка в пути — тоже. Плейсхолдер без значения у какого-либо варианта — отказ **до
нагрузки** (`EndpointConfig.require_path_params()`, его зовут и командная строка, включая
`--dry-run`, и `run_load_test`). Описание без значений годится только на то, чтобы вывести из
него операцию.

**Снимок конфигурации в файле прогона** берёт имена, а не значения: шаблон пути, база без
`user:password@`, имена заголовков (`header_names`) и параметров запроса
(`query_param_names`), метки вариантов. Значения заголовков, параметров запроса, тел и
`path_params` в него не попадают.

**Ошибки разбора не цитируют входные данные.** У моделей описания эндпоинта включено
`hide_input_in_errors`; ошибка профиля собирается из места и текста каждой ошибки без входных
значений (корневой адаптер объединения профилей этой настройки моделей не наследует), и
неизвестный `type` — «неизвестный тип профиля» без значения. Битый YAML сообщается файлом,
строкой и колонкой, без фрагмента.

Для того, кто зовёт библиотеку из своего кода, — три оговорки:

- `hide_input_in_errors` прячет ввод только из текста ошибки (`str(exc)`). Сам
  `ValidationError.errors()` и `.json()` ввод **содержат** (поле `input`); в журнал их без
  `errors(include_input=False)` не пишут.
- `repr(cfg)` убирает только учётные данные базы (а заодно `?query` и `#fragment`); значения
  `headers` и `query_params` в нём **видны**. В журнал и отчёт описание целиком не пишут —
  для этого есть `snapshot()`.
- Пароль, в котором есть `?` или `#`, в `base_url` пишется закодированным — `%3F`, `%23`:
  иначе это начало запроса или фрагмента, и разбор такой адрес отвергнет. `basic_auth()`
  отдаёт пароль раскодированным.

## Профиль

Поле `type` выбирает схему; неизвестный ключ — ошибка.

**Нагрузка задаётся двумя ручками, и они разные.** `workers × rate_limit_rps` — темп: столько
попыток отправки в секунду (в среднем на десятую часть меньше — пауза пейсинга несимметрична,
см. [[components/overview]]). Уровень параллельности фазы (`target_concurrency`, уровни
ramp и stress) — **потолок** одновременных запросов, а не их число: при быстрых ответах в
полёте меньше. Сверх того на воркера в полёте не больше `max_requests_per_worker`.

| Тип | Расписание | Что ещё |
|---|---|---|
| `linear` | разгон ступенями → плато `duration_sec` → спад | темп постоянный, растёт только потолок |
| `ramp` | фазы `phases`: уровень или перегон `start → end` подшагами | темп постоянный, растёт только потолок |
| `stress` | лестница от `initial_concurrency` до `max_concurrency` шагом `ramp_up_step`, предел `max_duration_sec` | на уровне L темп на воркера `rate_limit_rps × L / initial_concurrency`, запросов на воркера не меньше `ceil(L / workers)` |
| `batch` | одна фаза на `target_concurrency` | список — варианты эндпоинта × `repeat_count`; фаза кончается, когда список пройден, `duration_sec` — предел |

Для stress это значит: первый уровень идёт в профильном темпе, а каждый следующий —
пропорционально быстрее, и отношение двух уровней — отношение нагрузок. Для linear и ramp
темп от уровня не зависит: при быстрых ответах подъём потолка нагрузки не прибавляет.

### Пороги остановки

| Профиль | Ключи | Как работают |
|---|---|---|
| `linear`, `batch` | `stop_on_error_rate` | раз в секунду внутри фазы и на её границе |
| `ramp` | `stop_on_error_rate`, `stop_on_p95_latency_ms` | так же |
| `stress` | `stop_on_error_rate`, `stop_on_p99_latency_ms`, `stop_on_5xx_rate` | на границе уровня; сработал — лестница не растёт, дальше `hold_after_breaking_sec` на том же уровне |

**Определение одно для всех профилей.** Порог проверяется на окне последних 300
**завершившихся** запросов (по моменту завершения, а не начала: медленный запрос, вернувшийся
таймаутом, попадает в окно тогда, когда вернулся) и применяется, когда в окне не меньше 150
запросов; у batch — не меньше размера списка, если он короче. Пороги включительные. Порог
доли (ошибок, 5xx) срабатывает только при ненулевой доле. Порог `0` значит «в окне проверки
есть хоть один случай», **а не** «до первой ошибки вообще»: у stress окно смотрят на конце
уровня, у остальных — раз в секунду, и единичная ошибка, ушедшая из последних 300 до проверки
(на темпе выше ~300 запросов в секунду это меньше секунды), не учитывается. Задержки — по
всем запросам, включая ошибки, таймауты и снятые на выдержке фазы (`error_type:
"cancelled"`); запросов, ещё не вернувшихся, окно не видит — см. [[proposals]].

Сработавший порог linear, ramp или batch останавливает текущую фазу (уже отправленное
дожидается) и отменяет следующие. Остановка видна в трёх местах: событие
`{"event": "stopped", "phase": …, "concurrency": …, "reasons": […]}` в `events` файла прогона
(список событий свободный, формат записи прогона прежний), строка «ОСТАНОВЛЕН» в сводке и
предупреждение в журнале. Код возврата — 0: остановка по порогу — результат прогона.

**Если обрывать было нечего**, событие другое — `breached` (те же поля), в сводке «ПОРОГ
ДОСТИГНУТ». Так бывает, когда порог достигнут после конца последней фазы и у batch короче
окна: там порог проверяется, когда вернулся весь список, и **не обрывает его, а отмечает
итог**. У stress порог на последнем уровне лестницы — тоже `breached`; удержание после
отказа идёт в обоих случаях.

События движка (`stopped`, `breached`, `batch_list`) стоят в **конце** `events`, после событий
фаз; различать их — по полю `event`.

Порог, который не может сработать (за весь прогон по номинальному темпу уйдёт меньше
запросов, чем нужно окну), batch короче окна и порог `0` у stress называются до нагрузки:
на `--dry-run` — в плане, на прогоне — в журнале.

**Итог batch** — событие
`{"event": "batch_list", "phase": …, "planned": …, "completed": …, "reason": …}` и строка в
сводке. Пройден ли список, считается по числу вернувшихся замеров; `reason` — `null`, порог
профиля (если он оборвал список) или предел времени `duration_sec`.

**Нагрузка фазы кончается вместе с фазой.** Запрос ждёт места под потолком фазы в
очереди; получивший его после конца фазы (время вышло или сработал порог) ничего не
отправляет и замера не пишет. Ни один запрос не уходит на стенд после конца фазы, и ни одна
задача фазы её не переживает, в том числе при отмене снаружи.

**Запросы, снятые на выдержке фазы** — бывшие в полёте, когда кончились время фазы и
выдержка (до 16 с сверх него), — замеры `success: false`, `error_type: "cancelled"`, с телом
варианта и длительностью до отмены. Они входят в долю ошибок и **во все задержки** (p50/p95/
p99, максимум, среднее, наклон деградации, пороги задержки), а их длительность — нижняя
оценка: запрос шёл не меньше. В «вернувшиеся» списка batch они не входят. Исключать ли их из
задержек — открытый вопрос, см. [[proposals]] (С1).

## Командная строка

| Флаг | Что делает |
|---|---|
| `--endpoints FILE`, `--endpoint KEY`, `--profile FILE` | обязательны для прогона |
| `--profile-name NAME` | имя профиля в путях результатов; по умолчанию — имя файла |
| `--results-root DIR` | куда писать прогоны |
| `--dry-run` | разобрать, проверить имена, операцию и `{placeholders}`, показать конфигурацию и план — и ничего не отправить |
| `--save-raw` | сохранить сырые результаты (см. ниже) |
| `--report FILE`, `--report-only`, `--plotly-js FILE` | дашборд, см. [[components/overview]] |
| `--log-level`, `--debug` | подробность журнала; трассировка неожиданной ошибки |

**План** печатается перед каждым прогоном и на `--dry-run`: фаза, потолок, темп всего
(попыток в секунду, номинальный), предел в полёте на воркера, для batch — размер списка, для
stress — удержание на уровне отказа (`hold_after_breaking_sec`, в итоге «до N с (+M с
удержания)»). Заметки о порогах на `--dry-run` печатаются в плане, на прогоне — один раз, в
журнал.

**Журнал.** Командная строка держит журналы `httpx`, `httpcore`, `h2` и `hpack` не ниже
`WARNING` при любом `--log-level`: на `INFO` httpx пишет каждый запрос с полным адресом,
включая значения `query_params`, а `h2`/`hpack` на `DEBUG` — заголовки, в том числе
`Authorization`. Кто зовёт библиотеку из своего кода, настраивает их сам.

**`--save-raw` пишет без маскировки.** В файл прогона уходят тела запросов целиком
(`payload`), до 500 символов тела ответа на каждую ошибку (`error`) и адрес каждого запроса
(`url`) с подставленными значениями `path_params` (учётных данных базы в адресе нет); у
снятых на выдержке (`cancelled`) тело варианта тоже есть. Там бывают
учётные и персональные данные. Команда печатает предупреждение в stderr при включении, до
нагрузки; справка говорит то же. Через API (`save_run_results(save_raw=True)`) то же
сказано в докстринге, без предупреждения: флаг передаёт сам вызывающий, а запись идёт после
нагрузки. Адрес с `path_params` уходит и в журнал: `DEBUG` для ответа не-2xx, `WARNING` для
неожиданной ошибки запроса. Маскировки нет: своей здесь быть не должно, а `partest.redact` пока
не подключён — см. [[status]]. Формат сырых результатов от этого не менялся.

Предупреждения схемы (`ConfigKeyWarning`: `batch_mode` или `repeat_count` не по умолчанию,
`full_url` в теле) командная строка печатает строкой в stderr с именем файла — и тогда, когда разбор упал; прогон они не останавливают. Через API это
обычное предупреждение Python: под `-W error` разбор падает.

## Чего нет

Раскрытия переменных окружения в YAML и выключения проверки TLS — ни ключом, ни флагом.
Состояние и планы — [[status]].
