# WIKI.md — схема документации

Здесь описано, **как устроена** документация этого репозитория. Знания нет — оно на страницах.
Читается один раз перед правкой доков; в обычной работе не нужен.

## Схема общая для всего семейства

Раскладка, frontmatter, ссылки и рабочие циклы описаны один раз и лежат в
`partest_client/docs/wiki/WIKI.md`. Здесь не повторяются: один факт живёт в одном месте.
Процедура правки — скилл `orchestra-wiki` в корне рабочего пространства.

Коротко, чтобы не открывать: три слоя — неизменяемые источники (вне репозитория),
производное знание (`docs/wiki/`), конвенции (этот файл плюс `AGENTS.md`). Каталоги —
`concepts` (почему), `components` (что есть), `howto` (как сделать), `decisions` (почему
именно так).

## Что своё у этого репозитория

**Ни одной цифры нагрузки в документации.** Достигнутый RPS, точка насыщения, перцентили —
свойства чужого стенда, а не пакета. Попав на страницу, они устареют в тот же день и будут
процитированы как характеристика библиотеки. Примеры пишутся с очевидно выдуманными числами.

**Два потребителя результата, и путать их нельзя.** HTML-дашборд читает человек; артефакт
`load.profile` читает карта «Веха». Страница, описывающая одно, не описывает другое.

**Формат `load.profile` — не наш.** Вид объявлен в `partest_atlas.artifacts`, контракт
`artifact-schema` в `orchestra/repos.yaml`. Изменение согласуется с владельцем и попадает
в оба `CHANGELOG.md`. В одиночку формат не меняется.

## Проверка

```bash
python ../orchestra/tools/wiki_lint.py --repo partest-load
```

Линтер ловит: отсутствующий frontmatter, страницы новее которых стал код (`sources:` против
`verified:`), битые ссылки, литералы версий, приватные данные в публичном репозитории,
страницы, потерянные мимо `index.md`.
